1. 为什么是 Electron，另外三个为什么排除

核心约束只有一条：素材是带透明通道的预渲染视频（每段动画是一个网页可以直接播放的视频文件，视频自带 alpha 通道，即「哪些像素透明」的信息）。谁能一致地播放它，谁就是候选。

候选判定理由
Electron采用Windows、macOS、Linux 三处都用自己的 Chromium（Chrome 浏览器的开源内核），同一段视频行为完全一致；后续做商城、背包、设置这些界面时，网页排版是效率最高的做法；参考实现的血泪教训现成可用
Tauri排除Windows 走 WebView2（Chromium 系）能播，macOS 走 Safari 的内核WKWebView，根本不播放带 alpha 的 VP9 视频，直接黑底。要预留 macOS 就不能选它
Flutter排除桌面端没有现成的视频播放组件，透明无边框窗 + 鼠标穿透 + 置顶这套组合恰恰是它的弱项，等于用 Flutter 做它最不擅长的事
Qt / PySide6排除能跑通（indesktop 就是），但那是 236 个 Python 文件、13.9 万行自研渲染引擎堆出来的，它甚至不做视频解码，而是把视频转成图片序列自己逐帧画。对 12 段素材和「一个人做」的规模完全不成比例

语言用 TypeScript（JavaScript 加了类型检查的版本，写起来像你熟悉的 Java：有接口、有泛型、编译期报错），包管理用 npm/pnpm，测试用 vitest（相当于 JUnit）加 Playwright（相当于 Selenium，但它能直接驱动 Electron 窗口）。

2. 总体架构

三层：主进程（碰操作系统）、渲染层（画界面和跑逻辑）、皮肤包（纯数据）。渲染层里的业务代码只认接口，不认 Electron 的窗口 API。

主进程 能碰操作系统

像一个普通桌面程序：建窗、置顶、托盘、读写存档、起子进程。它自己不画宠物。

3. 窗口模型：一整块盖住桌面的透明窗

不是「一只宠物一扇小窗、窗跟着宠物跑」，而是开一扇和主屏工作区一样大的透明窗，宠物是这扇窗里的一个元素，它移动只是重画，窗本身从头到尾不动、不改大小。

参照实现是 qqpet（Q 宠复刻版）的 createPetWindow，注释原话就是「覆盖主屏工作区的透明穿透覆盖层」，一份代码同时出货 Windows、macOS、Linux、Android。

const win = new BrowserWindow({
  ...screen.getPrimaryDisplay().workArea,   // 窗口尺寸 = 整个工作区
  frame: false, transparent: true, hasShadow: false,
  resizable: false, movable: false,
  focusable: false,                         // 永远抢不走你的键盘焦点
  skipTaskbar: true, alwaysOnTop: true,
})
win.setIgnoreMouseEvents(true)              // 默认整窗鼠标穿透

为什么单宠物也选它

多宠物这条好处没了，但剩下两条更硬：桌宠要能在整个桌面上散步、贴左右边缘，窗跟着宠物走就要每帧调一次系统接口改窗口位置；而「窗口改尺寸」是这个品类里故障最多的一件事——你原计划「平时 320×320，开游戏扩到 600×400」，在整屏覆盖层下根本不需要，游戏覆盖物直接画在这扇窗里。

四条必须做的保护，不是可选项

  1. 穿透关闭必须有超时兜底。渲染层说「要接住鼠标」时主进程记下时间，之后只要还想接住就按固定节拍重复发（实测用 250 毫秒）；超过 500 毫秒没收到，主进程无条件恢复穿透。少了这条，一次逻辑卡死就是整块屏幕鼠标失灵。
    注意「每次判定光标还在宠物身上就续期」这个说法会埋雷：光标判定是主进程推来的坐标变化驱动的，用户完全可能把手停在面板上不动——没有新坐标就没有续期，500 毫秒后鼠标被放开，下一次点击穿到下面的窗口。所以续期必须由时间驱动，不能由光标移动驱动。
  2. 整屏窗必须给全屏应用让路。置顶窗盖住全屏游戏和视频是必然结果。抄 qqpet 的做法：起一个 PowerShell 子进程，每 500 毫秒问一次系统状态（返回 2=全屏应用、3=Direct3D 全屏、4=演示模式），命中就隐藏宠物，退出就恢复。注意这是常驻子进程，Windows 下有三条规矩必须一起抄：隐藏控制台窗口、挂 Job Object 防它变孤儿进程、关机流程里禁止再启动子进程（否则阻塞关机）。
  3. 窗口默认不可聚焦。focusable: false，只在输入框出现时临时切换（做成一条消息，不是重启）。
  4. 要有命中区可视化调试开关。Ctrl+Shift+点身体把身体矩形画在屏幕上，再点一次消失。上一轮排查那块灰色矩形时最缺的就是这个，第一天就该有。原定用 F9，实现时发现走不通：这扇窗故意 focusable: false，永远收不到键盘事件；改成系统级快捷键又会把 F9 从所有应用手里抢走，为一个调试功能不值。
这条架构已验过，2026-11-02 通过。整屏透明合成 + 保留硬件加速（让显卡参与把各层画面拼成最终屏幕影像，dsh-pet 为了绕开透明窗的 bug 把它关掉了，代价是视频全靠 CPU 占用高）在 Intel Arc 130T、200% 缩放的机器上实测成立：宠物框之外 580 万个像素里不透明像素为 0，真实屏幕差分在覆盖层范围内意外变化为 0，24fps 一帧不丢，CPU 稳态 1.4%。完整数据与截图见 spike/README.md。

一条硬限制：不能用 <video loop>。实测每次循环回到起点都要重新缓冲一下（70 秒里 17 次，素材正好 17 圈）。切动画必须靠双播放器提前 loadeddata 再换，这就是第 7 节那套 A/B 旋转的存在理由；Task 7 做完要回这里复验切换点无停顿。

还没验的两项：穿透在操作系统层面是否真的把点击让给桌面（要人手点一下），以及全屏让路（Task 13 的活，本轮预期就是盖住）。

4. 鼠标穿透怎么工作（这块最容易想错）

穿透是整窗级别的开关，没有像素级。打开它相当于把窗口从系统的鼠标命中测试里整个摘掉——用 Swing 的话讲就是让它从 componentAt() 的查找链里消失：画面照旧显示，鼠标永远找不到它，点击落到下面的浏览器上。

由此推出三条：穿透开着时你的网页收不到 mousemove，事件根本不会进来，所以「鼠标移到宠物身上」不能靠网页的悬停事件，必须从外面把光标位置拿进来；这就是为什么两个参考项目都在轮询——dsh-pet 每 60 毫秒取一次，qqpet 每 33 毫秒把光标推进网页；qqpet 选轮询的理由写在注释里：Linux 的穿透窗收不到任何鼠标事件，用轮询三个平台可以走同一条路。

官方 API 里有个捷径 forward: true（穿透状态下仍把悬停消息转发进来），但不能当主路径。两个真正出货的跨平台项目都没在 Linux 上用它：qqpet 的注释直说「Linux 上穿透窗收不到鼠标事件，渲染端没法靠悬停判定」，dsh-pet 为此单独写了 341 行读 X11 光标的代码。Windows 上它也不可靠——官方文档写明当前聚焦的窗口权限级别更高时 forward 会临时失效，原因是一个叫 UIPI（用户界面隐私隔离，防止低权限程序窥探高权限窗口的输入）的系统安全机制：你聚焦了一个以管理员身份运行的程序，或者打开了任务管理器，宠物就点不动了。macOS 支持这个捷径，但我们整条链路都不依赖它，所以三平台一句判断都不用写。

本项目采用的时序

1. 主进程每 33 毫秒取系统光标位置，换算成窗内坐标，发给渲染层
2. 渲染层用纯函数判定：这个点在不在当前动画的身体矩形里
3. 在 → 发一条消息请主进程关闭穿透；不在 → 请它打开穿透
4. 主进程对「关闭」状态记时间戳，500 毫秒收不到续期就自行恢复穿透
5. 拖拽期间完全忽略位置判定，直接保持接住状态（否则宠物跟不上手，松手事件也会丢）

裁决放在渲染层而不是主进程，理由是只有画宠物的一方知道此刻它的轮廓在哪——趴下、躲藏这些动作会把轮廓改掉一大截。

悬停面板带来的第三种区域：控件矩形

面板要能按按钮，就必须让那一块接住鼠标，所以此刻屏幕上同时存在三种区域，不能只有「身体 / 其余」两态：

区域鼠标行为穿透状态
身体矩形可点、可拖；悬停满 400 毫秒触发面板接住
面板矩形（控件矩形）按钮可点，输入框可输接住
其余全部透明区域穿过，落到下面的窗口穿透

判定与释放的顺序：光标进入身体矩形开始计时，停留满 400 毫秒才弹面板（避免鼠标路过就闪）；面板一出现就上报自己的矩形，此后只要光标在「身体 ∪ 面板」里就保持接住；光标离开两者 400 毫秒后收起面板并恢复穿透。这套数值直接继承 dsh-pet 的 OFF_BODY_RELEASE_MS = 400，它是踩坑踩出来的，不是拍脑袋。

两条硬要求：面板存在期间渲染层每帧续期，第 4 节那条 500 毫秒超时兜底照旧生效——渲染层一旦卡死，穿透自动恢复，鼠标不会失灵（面板可能留在画面上，但这是可接受的失败方向：宁可面板僵住，不能整块屏幕点不动）。面板上必须有明确的关闭途径，因为面板矩形内的点击全部被桌宠吞掉，本来该落到下面窗口的操作会失败。

面板上有输入框时（改名、将来的对话），窗口要临时切换成可聚焦：focusable: false 的窗口收得到点击、按得了按钮，但输不进文字。这条做成消息随时切换，不重启窗口。

一个红利：面板画在整屏覆盖层里，不会被窗口边界裁掉。dsh-pet 那边专门为此头疼，注释写着「桌面窗口只比宠物大一圈，超了会被裁」——它的窗口跟着宠物走，面板一宽就顶出窗沿。

5. 皮肤包契约（自定义皮肤就是换这个目录）

一个皮肤 = 一个文件夹。程序不认识「缓存」这个名字，只认识包。目录：

  manifest.json
  animation/
    idle/巡检.webm

    drag/被拖.webm
  sound/点击.webm           （可选）

manifest 的字段

字段含义谁在用
formatVersion这份契约自己的版本号程序只认支持的范围，不认就报错停下，绝不猜测
canvas画布尺寸，锁 640×360所有素材对齐的尺子
feetLine脚底基准线，锁第 330 行宠物「站在」桌面的哪条线上
bodyBox身体占的矩形（画布坐标）贴屏幕边、命中判定
targetSize期望显示宽度 + 基准像素比决定素材该出多大分辨率，Retina 屏会用到 2×
animations每条动画：名字、loop 还是 once、能否左右镜像、bodyBox 覆盖、所属分组行为调度器按名字要动画
pools动作分组 + 权重（待机池、活跃池…）随机层读它，代码里不写死任何权重
hotspots可选，比如「头顶可摸」的区域后续养成与互动
一条重要设计：动画按名字取，绝不按位置序号取。dsh-pet 把动画放在数组里用下标寻址，配置文件里专门写着「勿在中间插入新档」——用 Java 说就是把枚举的 ordinal() 当业务主键用了，中间加一档全体错位。开放给用户做皮肤，这个坑必然被踩。我们改成 idle、eat 这样的名字：包里有这条就播，没有就退回待机。

校验规则（用户自定义皮肤必须有，否则你会收到无数「我的宠物不显示」）

  • 必需集合：待机、转身、移动、被点、被拖。缺任一条就拒绝加载这个皮肤，并把缺的那条名字说清楚。indesktop 叫 core_gaps，值得照抄的是它的做法：发布前把包真的装进临时目录跑一遍检查（目录结构、画布尺寸、每条视频能不能解开），通过才允许装载。
  • 可选缺失就降级，不报错：分组里没有动画，就播待机。
  • 素材体检：抽几帧统计透明通道的数值分布，如果发现本该全透明的背景区域存在明显残留，直接警告「这个皮肤有灰底」。这条是专门防你今天问我的那个问题在用户身上重演。
  • 内置一个纯色块皮肤，跑测试和给做皮肤的人当样板。

6. 素材管线（从生成到能播的七步）

管线（pipeline，指把原料一步步加工成成品的固定流水线，每一步的输出是下一步的输入）：参考项目是豆包出片 → 去水印 → 抠像 → 归一化 → 编码 → 校验。这条线的每一步都可能引入画质问题，前两步在外部服务，后四步是本地脚本，本地这四步你自己写。

步骤做什么关键术语与坑
① 参考图三视图，正面那张是所有视频的第一帧决定角色一致性
② 生成视频蓝幕背景，16:9，10 秒蓝幕不用绿幕：角色有荧光绿发光件，绿幕会把它一起抠掉
③ 去水印遮罩处理—
④ 抠像（把背景色识别出来并变成透明）按色相判定背景 → 写透明通道坑一：接近全透明的像素直接写 0，否则留下淡雾；坑二：透明区域的 RGB 要抹平，否则背景颜色会渗出边缘；两个参考项目都用绿幕脚本，蓝幕区间要自己重写
⑤ 归一化统一身高和居中位置，脚底对齐基准线这一步的缩放会二次损害边缘，尽量一次到位
⑥ 编码640×360（或 2 倍）带透明的 WebM（一种视频容器格式，浏览器原生支持），VP9（一种视频压缩算法）+ alpha坑三：转码必须显式指定 VP9 的编解码器，用默认路径会静默丢掉透明通道；坑四：不能走会把透明通道做「色度二次采样」（把颜色/透明信息降一半分辨率存，省体积但边缘发虚）的中间格式；质量档位用 CRF 10 以下，不要学 dsh-pet 的 30（CRF 是「质量优先」模式下的档位，数字越大越省、越脏；它压到 30 是因为有 109 段要控制体积，你第一版只有 6–7 段，不必受这个约束）
⑦ 校验首末帧是同一姿势、透明通道存在、背景残留检查参考项目的校验脚本只查「透明通道有没有丢」，不查残留浓度，你要补
整条管线只有一条硬合同：每段动画的首帧和末帧必须是同一个标准正面站立姿势。因为视频按关键帧（完整存一帧的画面，中间帧只存「和上一帧差在哪」）压缩，播放器没法从任意时刻干净切入，只能整段从头播。两段动画能接上的唯一办法，就是它们都从同一姿势起、回同一姿势止。这是合同，不是审美。

另外，第一版就决定素材的像素比（1 个逻辑像素对应几个物理像素；Mac 的 Retina 屏是 2）。640×360 放大到 2 倍屏上会糊，qqpet 为此把素材重绘成 @2x。如果等皮肤做完才发现要改分辨率，第一版那 6–7 段得全部重出。

7. 播放器抽象：一个接口，两个可能实现

业务代码只调接口，不知道底下是视频还是图片序列。等价于 java.sql.Driver：上层面向接口，实现可换。

方法干什么为什么现在就留
prepare(name)把下一段动画提前加载到能画的状态不预加载，切换瞬间会空一下
play(name, loop|once)播一段行为链入口
onEnded播完通知外面「播完再抽下一条」整条链靠它
cancel()立刻停下拖拽、被打断、后续的事件驱动
frameIndex()现在第几帧动画和位移必须按帧对齐，按秒会漂
hitTest(x,y)这个点在不在角色身上视频实现只能给矩形近似，接口留着，将来图片序列实现给逐像素
snapshot()当前帧的画面粒子、特效、截图调试

双视频换帧的四条铁律

做法是放两个视频元素轮流当前台，一个在播、另一个在后台偷偷加载下一条。四条规则里三条是异步回调的老毛病：

  1. 等新的那个真的准备好（收到 loadeddata）再切换，不要在设置地址那一刻切。= Future 还没 complete 就去取结果
  2. 每次切换带一个递增的代际号，回调回来时号不是最新的直接丢弃。= 给异步任务打版本号，防止后到的旧结果覆盖新状态
  3. 退到后台的视频必须把「播完」监听器摘掉。= listener 忘了 unregister，它在后台播完照样触发，把正在播的动画杀掉
  4. 切换用 0.18 秒透明度渐变垫一下，硬切看得见接缝。
为什么要抽这层：行为调度器不认识视频标签，测试时塞一个假实现进去（像单测里用 FakeClock 或 Mockito 打的桩），不用真等 10 秒视频播完就能验整条行为链。第二、三轮的数值和游戏逻辑能不能写成单元测试，全看这一条。

8. 行为调度：固定规则决定状态，随机决定动作

你说「随机展示或者以一种固定的规则来展示」，这两件事不该二选一，它们是上下两层：

规则层（确定性，可单测）——根据时间和上下文决定现在处于哪种状态：
· 连续 N 分钟没有任何交互 → 自主活动态（可以在待机池和移动池里抽）
· 鼠标离得很近或在别的窗口里密集打字 → 安静态（只播待机，不移动）
· 深夜时段 → 休息态
· 被点、被拖 → 立刻进回应态，播完回上一个状态

随机层（在该状态的动作池里按权重抽）——权重全部来自皮肤的 manifest，代码里一个数字都不写。抽的时候排除当前这条，避免连着播同一个动作显得卡住。

随机层要能测试：随机源是注入进来的，测试时传一个固定种子（Java 里 new Random(seed) 的思路），同一条测试跑十次结果一致。

三个参考项目在这件事上撞成了同一个形状，可以当作定论：一个动作可能有多条变体（Q 宠是 Eat1.swf/Eat2.swf，dsh-pet 是加权池，indesktop 是概率骰子）。另外 Q 宠的皮肤目录里还有 happy / peaceful / sad / upset / prostrate 五个心情分组，这给你第二轮的数值提供了一个不需要硬编码映射的答案：心情档位决定用哪一套动作池，目录结构本身就是映射。

9. 交互层与存档

交互

  • 单击、双击、拖拽、拖拽松手后的抛物（带重力和落地反弹）、右键菜单。菜单是独立的一扇普通小窗，不挤在覆盖层里——覆盖层永远不改尺寸。
  • 拖拽期间命中判定完全让位给输入逻辑，不抢位置。
  • 需要输入框（改名、将来的对话）时才临时把窗口切换成可聚焦。
  • 小游戏分两类：需要宠物亲自参与的（传球、钓鱼）画在覆盖层里，用 Canvas 2D（网页里的画布元素，可以用代码逐帧画图形，适合球、水面、粒子这些会跟着手动的东西）；不需要宠物参与的将来另开普通窗口。
  • 悬停面板是这一层的主要产出：光标在身体矩形内停留满 400 毫秒弹出，面板上报自己的控件矩形，光标离开身体和面板 400 毫秒后收起。第一版按钮只做一件事——切换动画（待机、移动、转身、被点、被拖各一个按钮，外加「重播当前变体」），用来验证整条播放与穿透链路。面板尺寸不受窗口裁切，因为画在整屏覆盖层里。

存档

一个 save.json 放在系统的应用数据目录（Windows 是 %APPDATA%\<应用名>，macOS 是 ~/Library/Application Support/<应用名>），路径必须走一个函数，不许在代码里写死。写之前把旧文件备份成 save.json.bak（qqpet 的做法），文件里带 version 字段和一段迁移逻辑——dsh-pet 有 415 行配置但没有版本号，是明确要避开的反模式。提供导入导出。

关于养成数值，第一版按「冻结写入通道，但不写空壳逻辑」处理。具体就是两件事：存档结构里预留 stats 节点（四个字段先存在、值固定，不参与任何判断），以及把「谁能改数值」收敛成一个函数入口，第一版只有面板上的动作按钮会经过它。而衰减公式、离线补算这些第一版没有调用方的逻辑不提前写——提前写出来的东西没人验证，到第二轮做数值时既可能算错、又要重测一遍，是负债不是预留。这样做的收益是：第二轮加数值时，存档结构、读写通道、面板按钮三处都不用动，只往里填数字。

11. macOS 预留：现在只做四件事

好消息：macOS 是这套架构里最省事的一头。参考项目整个仓库里跟 macOS 有关的判断只有 31 处命中，集中在六类事情上（置顶层级降为 floating、不启用缩放补偿、可用区域要顶到屏幕上沿并保留 Dock 排除、托盘图标按模板图处理并隐藏 Dock、全屏由系统自己让路、存档路径换位置），而且 qqpet 用同一份窗口代码出货了 macOS 的 Intel 和 Apple 芯片两个安装包。

现在要做的只有四条，代价都不到一天：

  1. 平台层只暴露四个动作：建窗、穿透开关、光标推进、焦点切换。业务代码里不许出现 Electron 的窗口 API。
  2. 几何一律向平台层要「可用矩形」，业务代码不自己区分工作区和整屏面板。
  3. 素材的后缀和分辨率做成配置项。dsh-pet 给 macOS 留了第二条视频格式（HEVC 带透明通道的 .mov，用户自己下载后把播放常量从 .webm 改成 .mov），那是硬件解码的优化，不是前提；但「后缀是个配置」这件事现在定，将来不改代码。
  4. 主路径不依赖 forward，顺带把今天 Windows 上的 UIPI 失效问题一起解决。

现在不用管：Stage Manager、刘海遮挡、多显示器排列、mac 的代码签名与公证。

12. 测试与 v1 验收

13. 术语表

渲染 / 渲染进程
把数据画成屏幕上的像素这件事叫渲染；负责画的那半个程序叫渲染进程。类比：Swing 里那块画布和它的绘制线程（EDT），只是它的排版语言换成 HTML/CSS。
主进程
程序的主体，能建窗、读写文件、起子进程。它自己不画界面，类比容器/服务层。
IPC
进程间通信。两个进程之间约定的消息名和参数类型，等价于内部 RPC 接口定义。
合成 / 硬件加速
把窗口各自的画面拼成最终屏幕影像的过程叫合成；交给显卡做就是硬件加速，交给 CPU 做就是软件合成。透明窗在这个环节最容易出边缘故障。
透明窗 / 分层窗 / DWM
让窗口可以部分透明的机制。Windows 上是分层窗口样式 + DWM（桌面窗口管理器）负责合成；macOS 是另一套。
鼠标穿透
让鼠标「穿过」窗口落到它下面的窗口。整窗级别的开关，无像素级。
alpha 通道
每个像素的透明度信息。桌宠靠它把背景变成透明。
抠像
识别出背景色并把它变成透明。英文 chroma key，蓝幕/绿幕都属这类。
关键帧
完整存一帧画面，其余帧只存「跟上一帧差在哪」。这决定了视频不能从任意时刻干净切入。
色度二次采样
把颜色或透明信息按一半分辨率存储以省体积，代价是边缘发虚。透明通道走这条路必然产生灰雾和白边。
CRF
质量优先模式下的压缩档位，数字越大越省体积越脏。dsh-pet 用 30，你只有 12 段，用 10 以下。
管线（pipeline）
原料一步步加工成成品的固定流水线，每步输出是下步输入。素材管线 = 生成视频到出 webm 那七步。
状态机
有限个状态 + 状态之间的转换条件。桌宠的「现在该播哪段动画」就是一台状态机。
帧序列 / 帧率
每秒多少帧决定流畅度；帧序列是把动画存成一串图片而非一段视频，能任意跳帧，代价是体积大。
像素比（DPR）
1 个逻辑像素对应几个物理像素。Mac 的 Retina 屏是 2，Windows 的 125%/150% 缩放是另一套世界。
Canvas 2D
网页里的画布元素，用代码逐帧画图。球、水花、粒子这些跟手的东西用它，不用视频。
代际号
给异步操作打的递增序号，回调回来时号过期就丢弃。等价于给 Future 结果做版本校验。
预加载 / 预热
提前把素材加载到能立刻显示的状态，避免切换时空帧。
冒烟测试（smoke test）
只确认「程序能起、能显示、能退」的粗粒度检查，不验细节。
spike
为回答「这条路走得通吗」而做的丢弃式小实验。本项目的第一个 spike 是整屏透明窗四步验证。
UIPI
Windows 的用户界面隐私隔离：低权限程序碰不到高权限窗口的输入。它会让穿透转发功能临时失效。

14. 还没定的事

  • 最终用哪个角色形象。鲸鱼娘形象原作者以「署名 · 非商业 · 相同方式共享」开放二创但禁止商用；「缓存」是你已有完整设定的方案。练手可以用前者，发布的产品必须用后者或自研形象。
  • 第一版动画到底几段、先出哪一段。建议先出待机，因为它是所有其他段对齐的基准。
  • 三件从 v1 清单里掉出去的事要不要补回来。①「扔」这个交互从没进过 14 个任务；②右键菜单同样缺席，目前只有悬停面板一个入口；③存档导入导出没做，而原版 QQ 宠的存档兼容靠它。三者都是功能而不是缺陷，但清单写了就该有交代——要么排进 v1.1，要么明确划掉。
  • 蓝幕抠像脚本自己写还是改造。参考项目的脚本是绿幕专用，蓝幕区间和判定阈值要重写。占位皮肤走通了 ffmpeg colorkey 最简管线（tools/make-test-skin.mjs），但那是色块，换成真实角色素材时的容差与溢色处理还没验。
