**结论：通过，可以按整屏覆盖层往下做。** 但带一条硬限制——**不能用 `<video loop>`**，每次循环重启会卡一下，动画切换必须走双播放器预热（Task 7 本来的设计）。

## 四步实测

### ① 边缘：没有灰雾、没有黑边、没有矩形底

两条独立证据，都出数不靠眼。

**页面合成层**（`webContents.capturePage`，5,804,160 个像素）：宠物框与提示框之外，alpha 大于 8 的像素 **0 个**，alpha 最大值 **0**。也就是渲染层压根没往该透明的地方画东西。

**真实屏幕**（`desktopCapturer` 抓 DWM 合成后的画面）：先把窗口藏起来拍一张，再显示出来拍一张，逐像素做差。比较范围限定在覆盖层自己占的那块（919,360 像素），落在预期矩形之外的变化像素 **0 个**，变化总数 59,582 全部在宠物框和提示框里——正好等于色块面积 52,800 加提示框面积 58,240。

`spike/out/crop-pet.png` 是裁出来的实拍：色块压在浏览器正文上，两侧的文字一路延伸到色块边缘，边缘锐利，上下左右都没有第二层底色。

### ② 流畅：满帧，占用低且稳定

70 秒和 120 秒各跑一轮。每 10 秒一个采样点的视频帧计数增量是 **208, 239, 240, 239, 240, 239**——素材是 24fps，也就是**一帧没丢**。

CPU（各进程相加，单核百分比）：`1.73, 2.2, 1.41, 1.42, 1.45, 1.41, 1.43`，稳态约 **1.4%**。内存：Browser 93→115MB（涨的 22MB 是截图缓冲区，不是泄漏）、GPU 309→301MB、Tab 93→94MB，无增长趋势。

`gpu_compositing: enabled`、`video_decode: enabled`——解码和合成确实都在显卡上，这是 dsh-pet 关掉硬件加速之后没拿到的那条路径。

**唯一的问题**：70 秒里出现 17 次 `waiting`→`playing`，素材 4 秒一圈共约 17 圈，**几乎每次循环重启卡一下**。原因是 `<video loop>` 回到起点时要重新缓冲。对生产的直接影响：切动画不能靠 `loop`，必须提前把下一段 `loadeddata` 好再换，这正是 Task 7 双播放器的存在理由。Task 7 完成后要回到这里复验一次切换点无停顿。

### ③ 穿透：软件链路已通，系统层待人工确认

光标推进 151 次采样、命中翻转 8 次，每次都带光标坐标，抽查一致：`(576,439)` 落在宠物框 400–720 × 300–480 内判「接住」，`(473,281)` 在框外判「穿透」。主进程轮询 → 渲染层判定 → IPC → `setIgnoreMouseEvents` 这条链是通的。

没验证的是操作系统层面：穿透开着的时候点桌面图标是否真的落到下面。这一步只能人手点，见下面清单。

## 顺手挖出来两条生产级坑

这两条都不是 spike 特有的，生产代码必须照做，已写进设计文档第 10 节。

1. **主进程入口不能写顶层 `await`。** `await app.whenReady()` 放在 ESM 入口顶层会死锁：Electron 要等入口模块求值结束才触发 `ready`，而模块在等 `ready`。最小复现是两行——`console.log('before')` 打得出来，`await` 之后那行永远打不出来，进程挂着不退。写成 `async function main() { await app.whenReady() } ; void main()` 就正常。
2. **`ipcMain.on` 必须挂在 `loadFile` 之前。** 上一轮我把监听挂在 `await win.loadFile()` 后面，渲染层在 `requestAnimationFrame` 里上报的矩形就丢了，主进程只能回退到写死的宠物框，结果把提示框的白底和文字变化误判成「覆盖层漏色」，凭空多出 58,200 个不透明像素和 3,933 个差值像素。差点点把这条架构判死。

还有一条方法论：**屏幕差分必须限定在覆盖层自己的矩形内。** 第一次跑全屏幕差分时 `outsideExpected` 报了 322,320，看着像灾难，实际是两次截图之间桌面上别的应用（包括我自己所在的这个窗口）动了。范围一收，真实数字是 0。

## 追加：快拖后「屏幕上残留一块」是远程软件的锅

用户从远程桌面软件里看到快速拖动后某处残留一块、过一会儿自己消失。这类问题只能在真实桌面上看像素——
渲染层内截图拿到的是图层内容，「让出来的脏区有没有被重画」是 DWM 最终合成的事。

`node spike/ghost-probe.mjs` 在本机 DWM 桌面帧里找**只存在一帧的色块**（团块签名，不靠坐标换算）：
5 次真实快拖、每次位移 800–1145 CSS px，松手即刻 / +250ms / +850ms 三档采样，瞬态团块为 0。

代码侧对得上：两个 `<video>` 同在一个 `translate()` 的 `.pet-sprite` 里，退位槽是 `pause()` + 掉
`is-front`（0.18s 淡出），调试框每帧按 `hitBox()` 重画——没有任何一处能把像素留在宠物让开的区域。
所以那是远程软件的画面流缓存，不是桌宠。

真实角色素材进场后值得再跑一次：不透明区域更大，视频走 GPU overlay 的路径也不同。

## 追加：面板开着时整块屏幕被扣住 400 毫秒（已修）

真机症状「鼠标从宠物移出去后点别处发顿」。`node spike/grab-probe.mjs` 量的时间线：

| 场景 | 修前放开鼠标 | 修后 |
|---|---|---|
| 掠过宠物就走（面板没开） | 2ms | 3ms |
| 悬停叫出面板后甩出去 | **407ms** | **3ms** |

根因是 `wantGrab` 里那项 `panel.isOpen`。穿透是**整窗**粒度，面板还开着但光标早已离开
身体和面板的那 400 毫秒里，整块屏幕都不穿透，点击全被透明层吞掉——所以要点两次。
400ms 的收起延时本来只管可见性（路过就闪、一走就收会让按钮点不着），不该顺手把鼠标也扣住。

修法只有一处：`wantGrab = over || overPanel || dragging`。光标回到面板矩形里下一拍
（≤33ms）就重新接住，人手从移到位到按下远不止这点时间。
回归保护在 `e2e/pet-check.mjs` 的「光标离开身体与面板后立刻放开鼠标，不等面板收起」。
