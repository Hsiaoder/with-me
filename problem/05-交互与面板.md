# 交互与面板

---

## 5.1 鼠标停在宠物上不动，面板 400ms 后并不出来

**症状**：规格写「悬停 400ms 出现面板」，真机上要再动一下鼠标才弹；移开也不收。
**根因**：主进程对**相同坐标去重**（`cursor.ts` 只在坐标变化时发消息），
而悬停计时只在收到光标时检查是否满 400ms。手真的停住 = 没有第二次事件 = 计时永远差一脚。
**修法**：`hover` 增加 `pendingMs(now)`（离下一次自动开/关还剩多少毫秒，没挂起返回 null），
渲染层按这个值自挂 `setTimeout`，到点用最后那个坐标重喂一次 `onPoint`
——顺便重算命中框，因为是走动的宠物撞上停住的光标。拖拽按下时把这个定时器撤掉。
**怎么验**：e2e 改成**只喂一次坐标**再等 460ms 断言弹出（原来在等待后又喂一次，
验的是"第二次事件到来时算得满 400ms"，等于绕过了真实场景）。
**教训**：静止是桌宠的常态，不是边界情况。凡是"事件驱动"的判定，都要问"没有新事件时谁推进它"。

## 5.2 拖到右上角松手，宠物掉回地面

**症状**：用户原话「5，拖过去之后松开，又回到原位置了」。
**根因**：`pointerup` 里调了 `motion.snapToBottom()`——它只重置 `y`，把高度强行拉回地面线，
而 x 留在松手处，所以看起来像"跳回原位"。计划里本来就写着「松手停在原地，不跳回」。
**修法**：删掉那一次调用。启动落地仍由 `bootstrap` 里的 `snapToBottom` 负责；
`setPosition` 已经把 y 夹在屏幕内，不需要再吸。
**怎么验**：e2e 原来只断言 `after.x !== start.x`，所以这 bug 一路绿灯；
改成松手前后 **x、y 两轴都比** + 断言没有掉回地面。
**教训**：测"位置变了没有"要逐轴比。只比一个轴的测试等于没测。

## 5.3 收起的面板还在吃点击、还在把手型改掉

**症状**：用户原话「点击宠物，然后移到其他软件上，鼠标是手指，要点一下才正常」。
**根因**：样式优先级。UA 有 `[hidden]{display:none}`，但我们的作者样式
`.pet-panel{display:flex}` 压过它——所谓"收起"只是透明度 0，元素还占着 275×44、
还参与命中测试，命中的又是带 `cursor:pointer` 的按钮。光标形状按命中元素画，看不见也照画。
**修法（两步）**：先补 `.pet-panel[hidden]{pointer-events:none}` 止血；
随后彻底改：收起 = `display:none` 真移出布局（淡出靠 `transition: ... display .18s allow-discrete`
+ `@starting-style` 保住）。
**怎么验**：`spike/panel-hit-probe.mjs` 按面板自己的矩形取样，
修前 `命中=BUTTON[转身] cursor=pointer`，修后 `display=none`、命中不到；
e2e「面板收起后真的移出布局」红→绿。
**教训**：`opacity:0` ≠ 不可交互。UI 组件的"隐藏"要一次把布局、命中、光标三件事都交代掉，
否则残留下一次以另一种症状回来。

## 5.4 面板的矩形不该由面板自己上报

**症状**：面板一度每次打开都量一次 `offsetWidth` 并把矩形交给命中判定；
一旦改成 `display:none`，量到 0，命中就废了——两条约束互相打架。
**根因**：命中判定有**两本账**：DOM 里真实摆着什么，和面板自报的矩形。
**修法**：对齐参考实现 qqpet：面板根节点挂 `data-hit`，命中判定一律
`elementFromPoint(p).closest('[data-hit]')`，`rect()` 整个删掉（只剩夹屏幕用的 `size()`）。
身体那块仍按皮肤契约的 `bodyBox` 算——宠物是 `pointer-events:none` 的 `<video>`，问 DOM 问不到它。
**怎么验**：`test/panel-dom.test.ts` 断言 `data-hit` 在根节点上、`closest` 爬得到；
e2e 的位置/收起/命中三条检查全部改问 DOM。
**教训**：一个事实只留一份记录。"谁该接住这点鼠标"由布局回答，不由谁上报回答。

## 5.5 收起延时长到 1500ms：可见性延时不该管鼠标

**症状**：面板在按钮之间走位时就自己收了；同时"离开 400ms 收起"这个数本身也定小了。
**根因**：`HOVER_RELEASE_MS=400` 同时充当了两个语义：面板还显示多久、鼠标还被扣住多久。
后者在 5.3/1.7 之后已经不存在了，前者 400ms 又太短。
**修法**：改名并分值——弹出仍 `HOVER_DWELL_MS=400`，收起用 `PANEL_HIDE_MS=1500`；
`wantGrab` 完全不看面板状态。
**怎么验**：e2e 两半：「离开满 1500ms 才收」（并在 500ms 处断言**还开着**）+
「离开后立刻放开鼠标，不等面板收起」。
**教训**：一个常量被两处不同语义共用时，改名比改值重要。

## 5.6 皮肤权重和 `turn` 池死在链路外

**症状**：审查发现——`pickAmbient()` 有完整单测，运行时**没人调用**；
规则层超时后每拍返回 `move`，宠物一路走到天荒地老。
**根因**：分层职责串了线。规则层替随机层钦定了池，于是 manifest 的 `weights` 形同虚设、
`turn` 永远不会自主出现。而且 `test/rules.test.ts` 里居然有一条"没人理会一直 move"的测试
把错误行为钉死了。
**修法**：规则层久无人理后返回哨兵 `AMBIENT_POOL`（`'*'`，池名正则不接受它，撞不上合法皮肤），
交出选池决策权；把"播完这条之后播什么"从渲染层抽成 shared 里的纯函数 `nextClip`，
e2e 用运行时那份 manifest 走它一次（钩子 `__petDebug.ambientNext(rng)`）。
**怎么验**：`test/behavior.test.ts` 的 6 条 `nextClip` 测试 + e2e 那条自主选池检查。
**教训**：接缝本身要成为被测对象。"逻辑测到了、装配没接上"是这类分层架构最常见的假完成——
而写死错误行为的测试会让它看起来像设计。

## 5.7 拖不到屏幕最边缘：夹的是舞台矩形，不是身体

**症状**：用户原话——「现在的角色拖拽时，不能拖到屏幕的最边缘，这是什么原因」。
左右都碰不到边，中间那段空白像被什么东西顶住了。

**根因**：`createMotion` 的夹取区间是**舞台矩形**（`minX = bounds.x`、
`maxX = bounds.x + bounds.w - STAGE_W_CSS`），而角色只占画布中间一块。
试穿皮肤的 `bodyBox` 是 `{x:191,w:264}`，640 宽画布左右各留 95.5 / 92.5 CSS 像素的透明空白，
舞台一贴边，身体离屏幕边还差这一整截。

**修法**：把「身体离画布边有多远」交给运动层——`MotionOptions.bodyInset`，
由渲染层装配时用 `bodyInsetOf(manifest.bodyBox)` 算好传入，夹取区间向两侧（和上方）扩出去。
空白是素材属性，不写死常量，换皮肤自动跟着变。

**怎么验**：`test/motion.test.ts` 的 bodyInset 两条 + e2e 那条贴边检查。
e2e 的拖拽目标点必须打到 ±99999 这种远远越过屏幕边的坐标：拖到「刚好不够」的位置，
量到的是没夹住的中间值，改错方向也能过——上一版就是这么假通过的。

**教训**：夹取对象要问「用户眼里角色的边界在哪个矩形」。画布自带的透明空白会让
「舞台贴边」和「身体贴边」差出一大截，而且这截随皮肤变，只能是算出来的。

## 5.8 要光标连续，就得让一截看不见的空隙吃掉点击

**症状**：用户原话——「我从宠物上移开，移到按钮上时，又变回原来的光标了」，
接着要求「按钮之间要连续，鼠标从宠物移动到按钮这一段也要连续」。

**根因**：两层。① 按钮自己写的是 `cursor: pointer`（Windows 的手形），和身体那枚 `hand_point`
是两套。② 更根本的：光标只在**窗口被命中**时才归我们——穿透开着时这扇窗收不到
`WM_SETCURSOR`，读到的是底下窗口的光标。而命中判定按 5.4 的规矩只问 DOM
（`elementFromPoint(...).closest('[data-hit]')`），于是身体与面板之间那截、
以及四个按钮之间那 8px 全是空隙 → 一路闪。

**修法**：交互区改成**身体框与开着的面板的外接矩形**（`unionRect`），光标、抢鼠标都用它；
`--pet-cursor` 只定义一次，按钮和设置底板各挂一处而不是赌继承。
关键是把两件事拆开：**区域管光标和抢鼠标，"算不算有人在使用"仍然只问 DOM 命中**。
所以停在看不见的空隙里不续命，1500ms 收起照旧跑，区域随即缩回只剩身体——
吞点击的时间有上界，5.3 那个「看不见却吃点击」的 bug 没有复活。

**怎么验**：`test/geometry.test.ts` 的 unionRect 四条 + e2e「交互区是连续的」
（身体—空隙—按钮三点都 `pet-over`，收起后同一批点全部落空）+ `spike/cursor-probe.mjs`
拿 `GetCursorInfo` 读系统口径：四个点同一个句柄 `hot=9,2`，空地是系统箭头。

**教训**：「连续」和「不吃看不见的点击」是一对真冲突，只能选边界，别指望两全。
这里的边界是：**放大只在面板可见期间生效，且不参与续命**。另外 qqpet 没这个矛盾——
它的窗口就只有宠物那么大，整窗挂个常量就够了，照抄之前先问它的前提我们有没有。

## 5.9 气泡也带 data-hit，读一句话就把按钮面板叫了出来

**症状**：e2e 连红两轮，报的还是两个不相干的样子——第一轮「刚进去就弹出了」，
第二轮「到点没收起」。

**根因**：一个耦合造成两个现象。气泡为了抢鼠标和手形也挂了 `data-hit`，
而面板的悬停计时问的是 `closest('[data-hit]')`——于是**光标停在气泡上被当成"用户在用面板"**：
一是 400ms 后把按钮面板叫了出来，二是让气泡自己一直被续着不收。
「抢鼠标」和「该不该叫出面板」本来是两件事，被同一个属性绑成了一件。

**修法**：拆开。悬停计时只认 `.pet-panel`（`closest('.pet-panel')`），
抢鼠标与光标仍然认整个交互区外接矩形（身体 ∪ 面板  气泡）。
气泡的续命走它自己的判据（坐标几何量矩形，不用 CSS `:hover`——穿透一开就收不到 `mouseleave`）。

**怎么验**：e2e 气泡那条同时钉两件事：光标压在气泡上时 `pet-over` 为真（进区域了），
而面板 `open` 为假（没被叫出来）。只验其中一条就是回到原来的耦合。

**教训**：加一个带命中权威的节点之前，先问「哪些判定在共用这个属性」。
`data-hit` 当时只有一个消费者，所以看起来等价；多一个消费者那天，等价就没了。

## 5.10 夹住屏幕顶，等于把气泡推到它最不该去的地方

**症状**：用户原话——「当我拖着宠物移到最上方时，气泡会向下移动盖住宠物」。

**根因**：`bubbleAnchor` 当初为了「不溢出屏幕」写了 `Math.max(screen.y, y)`。宠物贴顶时
身体上方只剩几十像素，夹取把整个气泡**往下推**，于是它盖在宠物头上——一个朝下的尾巴
指着一片空白，而气泡本该在的位置被它自己占掉了。

**修法**：去掉 y 的下界，允许负值。覆盖层只盖住工作区，窗口外的部分天然被裁掉，
宠物拖下来气泡就自己回来。横向照旧夹回屏幕内——左右「裁一半」是半吊子，
上下越界才是这个功能的本意。

**怎么验**：`test/geometry.test.ts` 钉两个数（气泡 160 高：身体顶 100 → y = −72；顶 20 → −152），
e2e 钉两件事：贴顶时 `top < 0` 且**气泡底不超过身体顶**；拖回中间时完全回来。

**教训**：「不许越界」不是免费的正确——先问越界的代价和被推回去的代价各是什么。
这里越界只是看不见，被推回去是挡住主体还指错方向。
另外「永远在宠物上方」这种约束，实现时要检查它和夹取会不会互相打架。

## 5.11 拖拽动画挂在松手上：整段拖拽它都在呼吸，松手反倒演「被拎着」

**症状**：用户原话——「现在点击拖拽的时候，动画有延迟」。

**先量，别猜**（`spike/drag-latency.mjs`，合成一次 916ms 的真实拖拽，逐帧采样）：
rAF 间隔中位 17ms / 最大 25ms（没被节流）；位移差中位 12px = 一步的距离，就是一帧的滞后；
拖拽期间前台一直是 `idle/breath.webm` 且 `currentTime` 连续推进。
`current.pool` 变 drag 是**松手后 14ms**，前台素材换过来是**松手后 30ms**。
所以管线一点不慢——**慢的是触发点**：`requestClip('drag')` 写在 `pointerup` 里，
按住的全过程根本没叫它。所谓"延迟"就是整段拖拽的时长。

**根因**：`pointerdown` 立刻把这次算成拖起，`pointerup` 才收尾并播动画，动画因此只能挂在松手。
这个耦合还带来第二个后果：**点身体走的是同一条路**，所以皮肤的 `click` 池（契约里的必需池）
从来没有触发点——上一轮清理台词时把 `click` 那一档删掉，理由写的就是"没有触发点"，
其实真正没触发点的是整个 click 池。

**修法**：加一条位移阈值 `DRAG_START_PX = 4`。
按下只记按下点；移动越过阈值那一刻才 `requestClip('drag')` + 台词；
松手时没过阈值算「点」→ 走 `click` 池（点了必须有反应，这轮先只给动画不给台词）；
过了阈值 → `rules.feed('dragged')` 后切回 `idle`。
切回 idle 不是可选：这套素材每条 10.04 秒，不切的话松手后它还继续演「被拎着」演到完。

**怎么验**：e2e 两条——`拖拽动画挂在「真的拖起来了」那一刻`（移动后同步读 `current.pool === 'drag'`，
等 250ms 读前台 `src` 必须已是 `drag/`，松手后必须回到 `idle/`）；
`点一下不动是「点」`（按下—松手全程 `current.pool` 不许出现 drag，最后必须是 click）。
真实输入那侧用探针复量：drag 从按下后 943ms 降到 **22ms**，前台素材 959ms 降到 **47ms**。

**教训**：「有延迟」有三种可能——渲染慢、素材解码慢、触发点挂错。先分段量（按下 / 决策 / 换片 / 出画），
再决定改哪一段；凭手感去调 `CLIP_FADE_MS` 或预加载素材会改错地方，因为那两段本来就只花 30ms。

## 5.12 直接 `panel.hide()` 收面板，鼠标停在原地就再也弹不出来

**症状**：给「点完食物即收列表」加了一行 `panel.hide()`，e2e 里后面所有靠悬停叫面板的检查全红：
「前置：列表收掉之后面板叫不回来」。不是偶发，是**再也叫不开**。

**根因**：「面板开着」有**两份状态**——`panel.isOpen`（DOM 上有没有 `hidden`）和
`hover` 状态机自己的 `open` 标记。悬停链路走的是 `onPoint` 返回 `'open'/'close'` 再动两边，
所以天然同步；但 `pick` 里我直接调 `panel.hide()`，**没人的通知 hover**，它还以为开着，
于是 `inside && open → return 'none'` 永远不再返回 `'open'`。要等一次「离开满 1500ms」把它的
`open` 翻回 false，面板才可能再弹——而用户点完食物鼠标就停在那儿，不动。

**修法**：越过悬停链路收面板时，先 `hover.reset()` 再 `panel.hide()`。
拖拽那条路（pointerdown 里）本来就是这么写的，只是没人把这条规矩写成注释，
所以加新调用点时踩了。`reset()` 会把 `enteredAt/leftAt/open` 全清、延时回动作档，
下一个光标点位重新起 400ms 停留计时。

**怎么验**：e2e 那条「点了食物但列表没收起」后面紧跟「列表收掉之后面板叫不回来 → 必须还能叫回来」，
再验一次 `panelView === 'actions'`。这条红过，修完绿。

**教训**：一个事实有两份表示时，任何"只改一份"的调用点都是潜在的死状态。
加新调用之前先找同类的既有调用点抄它的成对操作——这里 `grep panel.hide()` 有四处，
其中唯一一处越权收的（拖拽）就配了 `hover.reset()`，那才是答案。

## 5.13 一条 e2e 检查把面板留在「状态视图」，下一条就等一个不该存在的节点

**症状**：加完状态视图，e2e 一次红了五条。最怪的是那条「离开身体与面板满 1500ms 后面板自动收起」——
它自己没改过，却报「没收起」。还有一条是 `page.click` 等 `button[data-id="feed"]` 等了 30 秒超时。

**根因**：检查之间**共享同一个页面状态**，而状态视图是个会「留着不走」的状态。
「点状态按钮」那条检查断言失败就抛在半路，面板停在 `view: 'stats'`；
下一条 `openOnBody()` 看到 `open === true` 直接返回成功，可里面根本没有 `data-id="feed"` 那颗按钮
——它在动作视图里。于是「等一个不该存在的节点」= 30 秒超时。
第三条更绕：面板停在状态视图时收起延时是 `VIEW_HIDE_MS`（5000ms）而不是 1500ms，
那条检查按 1500ms 等，当然等不到——**它测的是真的行为，只是被测对象已经不是它以为的那个视图**。

**修法**：每条碰面板的检查自己收尾，不接上一条的残局：
`__petDebug.hidePanel()`（内部是 `hover.reset()` + `panel.hide()`，成对操作的理由见 §5.12），
需要特定位置的（右侧/翻边）先 `moveTo` 把宠物挪回中间再断言。
另外初值类断言改成**相对断言**：喂完食物只断言「比开机初值 70 高」，
不写死 84——前面已经喂过几次，写死就是在赌检查顺序。

**怎么验**：这轮新加的四条检查现在都自带前置（hidePanel + moveTo），
把它们的顺序在文件里挪动也不会翻红。这条当时是红的，修完绿。

**教训**：共享一个活体应用的检查，**收尾和前置一样是检查的一部分**。
断言里出现「精确数值」之前先问一句：这个数被前面哪条检查碰过？

**又犯了一次（2026-11-05，换食物底板素材那轮）**：新加的底板断言写成
`/button_rectangle_line_blue\.png$/`，而计算样式里是 `url("app://...png")`——串尾是 `")` 不是 `.png`，
`$` 永远不匹配，检查红在半路，面板停在食物视图。下一条「整屏步进」的前置是
`openOnBody()` + 点 feed，可它假设面板是关着的：面板开着时点身体是**收起**，
于是 feed 按钮又等 30 秒超时。同一类坑，两个症状。修法是两条都补自己的前置
（步进那条开头 `hidePanel()`），正则改成不带锚点。
**新踩点**：`openOnBody()` 这个名字骗人——它做的是「点一下身体」，面板本来就开着时这一点会把面板关掉。
凡是依赖「面板当前是关的」的检查，都得显式 `hidePanel()` 起手，不能靠 `openOnBody()` 兜。

## 5.14 面板从「悬停弹出」改成「点击弹出」：三处连带，漏一处就是死状态

**动机**：用户提的——整屏覆盖层上鼠标路过就出菜单太容易误触，改成点一下才出。

**连带一：`hover` 只剩一半职责。** 它原来同时管弹出（停留 400ms）和收起（离开 1500ms），
弹出那半边删掉后 `HOVER_DWELL_MS` 就成了没人读的配置——**跟着删**，留着下一个人会以为还有这条路。
`open()` 语义也从「计时器判定该开了」变成「调用方把面板叫出来了，开始计离开时间」。

**连带二：`pointerdown` 里不能再收面板。** 以前 down 立刻 `panel.hide()`（怕拖拽时面板飘在旧位置），
但点击开的东西必须能点击关——down 就收，`togglePanel()` 永远看不见「已经开着」这个状态，
再点一次收不掉。改成**真的拖起来（越过 4px 阈值）那一刻才收**，顺带 §5.12 那对
`hover.reset() + panel.hide()` 收进一个 `closePanel()`，调用点不用再记这个配对。

**连带三：e2e 的 `openOnBody()` 点完必须补喂一次光标。** 改完有两条检查红在
「前置条件：光标在身上，该接住鼠标」——因为 `grabRequested` 与交互区只在**光标事件**里更新，
点击路径根本不碰它。真实用户点宠物时鼠标就停在宠物上，所以 helper 要点完再 `feed(center)`，
否则测的是「点了但鼠标不在身上」这种现实中不存在的组合。

**怎么验**：e2e「点一下身体出面板，再点一下收起」把三条都钉住了——
先证明**停在身上不弹**（等过原来 400ms 的门槛，弹了就是没改干净），再证明点了开、再点关；
`test/hover.test.ts` 整份重写（弹出那半边删掉，收起那半边一条没少）。
351 单测 + 39/39 e2e。

**连带四（上一轮提交之后才撞出来的）：四个 spike 探针也在读「悬停弹出」这条路。**
`icon-shot`、`stats-shot`、`grab-probe`、`panel-hit-probe` 都用「喂光标 + 等 460/500ms」叫面板，
改完它们统一变成 `page.click` 30 秒超时。**测试套件跑绿不等于工具链没坏**——
grep 的范围必须包括 `spike/`，那些一次性探针同样是这段行为的读者。
顺带修掉一个老毛病：探针收尾的 `rmSync(ud)` 在应用刚退出时会 EPERM（句柄还没释放），
加 `maxRetries/maxRetryTime`，别让它报着错走人。

**教训**：改「什么时候出现」这类交互语义，先 `grep` 谁在读这个触发条件——
这次是四处：配置常量、另一条路径上的副作用（down 里的 hide）、测试的前置 helper、`spike/` 里的探针。
只改主路径而漏掉后三处，症状分别是「配置骗人」「toggle 失灵」「测了个不存在的组合」「工具链静默报废」。

## 5.15 面板从一个盒子拆成两块：外接矩形把侧面那块也算进去了

**动机**：用户提的——点喂食出列表时按钮整排消失，列表应该挂在按钮**下面**；
状态视图同理，但读数仍挂宠物右侧。

**结构**：`.pet-panel` 从「内容盒子」改成「定位层」（`inset:0`、不吃命中、只当 `data-hit` 宿主），
里面 `.pet-actions` 按钮条 + `.pet-plate` 副板各自 `transform`。
副板的锚点按视图分：列表走 `stackAnchor`（挂在按钮条**外侧**，跟着 `panelAnchor` 新报的 `side` 镜像，
中间那段永远留给身体），读数走 `statsAnchor`（右侧）。设置视图仍整块替换按钮条。

**踩了三处，都不是主路径**：

1. **气泡让路判错**。`bubbleAnchor` 靠 `panel.y + panel.h <= body.y` 判「面板在头顶」。
   状态栏挂在侧面，取两块的外接矩形后，矩形下沿低到身体中线以下，这条判据直接失效，
   气泡落回身体正上方，压在常驻的按钮条上。合成 `panelBox()`（给光标连续区，要外接）
   和 `bubblePanelBox()`（给气泡，状态视图只让按钮条）两个函数才分开。
   顺带补了 `openPanel` / `view` 回调里的 `placeBubble()`——面板一占位，正在说的话得跟着让。
2. **e2e 里所有量 `.pet-panel` 矩形的检查全部作废**（十处）：那个选择器现在量到的是整个视口。
   症状千奇百怪——「面板中线 800 没对上对称轴 1000」「停在空隙里把面板续住了」
   「`page.click` 等 feed 按钮 30 秒超时」（它算的 band 点跑到屏幕正中，喂进去的光标位置是错的）。
   逐条改问 `.pet-actions` 或 `.pet-plate`。
3. **固定 400ms 等 `display` 变 none 在长跑里不够**。`transition: display .18s allow-discrete`
   会把 `display` 留在旧值直到过渡走完；覆盖层没焦点时长跑里这个时机不稳，
   读到过还没换过去的 `block`。改成 `waitForFunction(display === 'none', timeout 4000)`——
   等条件而不是等时间。
4. **我在气泡那条检查末尾补了 `hidePanel()`，把下一条检查的隐式依赖照出来了**：
   idle 那条用 `feed(身体正中)` 当「打开面板」——可 `feed` 只是喂光标坐标，不点击。
   它一直能过是因为上一条检查收尾时面板还开着；面板一被收干净，`page.click(game)` 就等一个
   不可见的按钮超时。这是 §5.13 同一类坑的第三次，改法也一样：前置自己调 `openOnBody()`。

**教训**：把一个「大家都当它是矩形」的节点改成定位层，`grep` 要搜到**选择器字符串**这一层
（`querySelector('.pet-panel')`），而不只搜变量名；主路径的几何改动，测试与探针都是被动方。

## 5.16 「框上面也有一条影」：素材画的底影和 CSS 模糊溢出是两件事

**症状**：A 套配色落地后用户盯着食物列表说「不想要上面的阴影，只想让阴影出现在下面」。
直觉会先去翻素材——`button_rectangle_depth_line` 的暗边按 `depth_` 的语义**只有下边有**（§3.9 量过），
所以「上面那道」根本不归素材管。

**怎么确认是谁画的**：`capturePage()` 拿到的是透明窗，框外那些像素的 RGB 被预乘成 0，
**只有 alpha 有意义**。于是从底板矩形往外逐像素读 alpha（`spike/foods-shot.mjs` 的扫描线改成向外走）：

```
上沿外 -1 … -14 设备px：alpha 12 → 1     ← 板顶外面确有灰雾
下沿外 +1 … +13 设备px：alpha 27 → 7     ← 下面更重，符合「有投影」
```

上沿外有 12/255 的黑，说明有一层**四周都溢出**的东西——`.pet-plate` 的 `box-shadow: 0 2px 8px rgba(0,0,0,.16)`。
8px 模糊向四周各铺开约 4px，2px 的下偏抵不掉，所以上边也漏出约 6 CSS px（2× 屏上 12 设备 px）。
素材那道硬底影从头到尾只在下边，冤枉不了它。

**修法**：`box-shadow: 0 6px 10px -4px rgba(0,0,0,.22)`。负 spread 先把阴影矩形往里收 4px，
再下偏 6px，模糊半径 10 的一半（≈5px）就够不到上沿；下边反而比原来更实在。
`test/config.test.ts` 里加了一条读 CSS 的检查：`|spread| + Y偏移 ≥ blur/2`，写法改成 `0 2px 8px` 那种就红。

**教训**：透明置顶窗里「阴影」有两个来源——素材画的（跟着 slice 走，可以不对称）和 CSS 模糊（天生四周对称，
只能靠负 spread 或大下偏去破）。用户说「某一边有影」时先分清是哪一个，别拿其中一个去改另一个的症状。

## 5.17 点喂食后那颗按钮变成正方形：`background` 简写把圆底擦了

**症状**：用户原话「我现在点击喂食，然后喂食的按钮怎么变成正方形了」。

**这是我上一轮改出来的回归**。`.on`（当前视图高亮）以前只会落在**卡片里的文字按钮**上——
`renderActions()` 建按钮时永远传 `on=false`，所以圆底那五颗从来没带过这个类。
我为了让按钮条跨视图复用，新写了 `syncActive()`，它第一次把 `.on` 挂到了圆底上，
于是撞出这条一直潜伏的规则：

```css
.pet-panel button.on { background: var(--on-fill); ... }   /* 简写 */
.pet-panel button[data-id] { background: url("…/button_round_depth_line.svg") center / 100% 100% no-repeat }
```

`background` 是简写，会把 `background-image` 重置成 `none`。圆底就是按钮的背景图，
图一没，露出来的就是那个 40×40 的命中区本体——**正方形**。和 §3.10 那条
「`background` 简写会把 `background-clip` 重置回 border-box」是同一个坑的另一副面孔。

**修法**：两件事一起做，少一件都会再来一次。
① 卡片那条**限定作用域**：`.pet-plate button.on`（文字卡片都在板里，圆底都在 `.pet-actions`）；
② 圆底**另给一套选中态**，而且完全不碰背景——`border-radius: 50%` + `outline: 2px solid #6990A7` +
`outline-offset: 2px`，一圈留缝的同心环。用 outline 不用 box-shadow，是因为 shadow 会和卡片那条投影叠。

**怎么验**：`test/config.test.ts` 扫所有带 `.on` 的规则——**用了 `background` 简写的那条，
选择器必须含 `.pet-plate`**；再加一条「圆底的选中态规则里不许出现 background」。
观感由 `spike/foods-shot.mjs` 裁出来的 `actions-crop.png` 作证（喂食开着时第一颗该是圆 + 一圈环）。

**教训**：给一个**新元素**挂上一个**老类名**之前，先 grep 这个类名的所有规则。
「以前没人这么用」不是「这么用安全」——潜伏的样式只在第一个撞上它的调用方那里才现形。
