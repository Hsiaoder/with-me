# 渲染装配与生命周期

---

## 4.1 主进程入口写了顶层 `await`，直接死锁

**症状**：Electron 起来没窗口，也不报错，进程活着。
**根因**：Node ESM 的顶层 await 与 Electron 的 `app.whenReady()` 装配顺序冲突。
**修法**：入口不用顶层 await，一律 `void app.whenReady().then(...)`；
`app.quit()` 在 ready 之前调用不保证拦住回调，所以 then 里还要再挡一次锁标志。
**怎么验**：`npm run build` 后直接 `npm start`；入口形状写在 `src/main/index.ts` 顶部。
**教训**：Electron + ESM 的两条硬规矩：相对 import 必须带 `.js`；入口不许顶层 await。

---

## 4.2 preload 不能 import 任何东西

**症状**：把通道名从 `shared/ipc.ts` import 进 preload，沙箱里直接炸。
**根因**：`contextBridge` + preload 沙箱限制。
**修法**：`src/preload/index.cjs` 单文件、零 import、消息名字符串就地内联。
**怎么验**：`test/preload-contract.test.ts` 读那段内联字符串，与 `shared/ipc.ts` 逐个比对——
两边跑偏会立刻红。
**教训**：不得不复制的字符串，必须有一条测试把它钉在源头。

---

## 4.3 常驻 PowerShell 子进程的三件事

**症状**：全屏让路探测要在退出时干净收掉，脚本还先炸过一次。
**根因**：三个独立小坑叠在一起——
① `.ps1` 里写中文：WinPS 5.1 按 ANSI 读 UTF-8，解析直接失败；
② 子进程不知道父进程何时死掉，会变成孤儿；
③ 它可能在宠物正隐藏时死掉（见 [01-窗口与鼠标穿透.md](01-窗口与鼠标穿透.md) 1.11）。
**修法**：脚本内容**纯 ASCII**（要中文就 base64 走 `-EncodedCommand`）；
每轮检查 `Get-Process -Id $parent` 判父进程存活；`close` 事件里恢复显示；
`process.once('exit')` 里 kill。
**怎么验**：e2e 两条——「让路探测子进程已启动」「退出后没有残留的探测子进程」。
**教训**：拉子进程就欠三条债：怎么起、怎么确认它该活着、怎么确认它死了。中文这条坑我后来
在探针脚本上又踩了两次（见 06）。

## 4.4 退出时清理的顺序与残留

**症状**：审查指出 `startCursorPolling` 返回的停止函数被丢掉、租约 sweep 定时器没人管、
退出时可能向已销毁的 `webContents` 发消息。
**根因**：生命周期没有统一归属，各自散在装配代码里。
**修法**：`before-quit` 里集中：停轮询、清 sweeper、停让路探测，最后落盘
（落盘放最后，因为 `saveTo` 会刷新 `lastSeenAt`）；用 `closing` 标志防重入；
sweeper 加 `.unref()` 免得它自己拖着事件循环。
**怎么验**：e2e 的退出残留检查 + 人工看任务管理器。
**教训**：常驻定时器/子进程一律在装配处拿到"停止函数"，别等出问题再补。

## 4.5 新版本写的存档，被旧程序降级覆盖

**症状**：审查指出——注释说"版本高于支持范围时按默认值处理"，代码却照抄未来档的字段
并把 `version` 改写成 1，退出时无条件落盘。
**根因**：读盘和写盘是两个函数，中间没人记得这个档"我们没看懂"。
**修法**：`migrate` 真的回默认值，并带一个 `fromFuture: true` 诊断标记；
`saveTo` 见到它就**一个字节都不写**（连 `.bak` 也不生成，那份"备份"是从不认识的原文件复制来的）。
**怎么验**：`test/save.test.ts` 断言默认值真生效，`test/storage.test.ts` 断言写后原文件一字不变、
不产生 `.bak`。
**教训**：诊断信息（`warnings`、`fromFuture`）必须和"要不要落盘"这个决定绑在同一个函数里，
否则一定会被忘记。

## 4.6 Windows 上刚退出的进程还攥着文件句柄

**症状**：测试清理临时目录时 `rmSync` 抛 `EBUSY`。
**根因**：`force: true` 只忽略 ENOENT，不忽略 EBUSY；Electron 子进程句柄释放是异步的。
**修法**：清理包在 try/catch 里，清不掉就算了——临时目录归系统回收。
**怎么验**：e2e 稳定跑完不残留报错。
**教训**：Windows 上"删不掉临时文件"不是失败，别让它把测试整体判红。

---

## 4.7 渲染层不留 `destroy()` 是有意的

**症状**：两轮审查都提"rAF、心跳定时器、事件监听没有统一销毁出口"。
**根因**：不是遗漏——主进程用 `once('did-finish-load')` 推皮肤，页面既不 reload 也不热切换，
disposer 没有调用方。
**修法**：不写。在 `bootstrap()` 上留一段注释写清理由和"什么时候该补"（出现第二个装配点时）。
**怎么验**：注释即结论；将来加热切换或多宠物时按那段补。
**教训**：没有调用方的生命周期出口是空壳，还会给人"已经处理过了"的错觉——
项目自己的编码规则第 8 条就是为这个写的。

## 4.8 「每天第一次」的门槛只活在内存里：重启就能再领一次

**症状**（codex 复审 #3 P1）：面板每次打开都上报 `daily-open`，规则说 20 小时内只奖励一次亲密度，
但判断依据 `lastEventAt` 是 `startStats()` 里的一个闭包变量，**存档里没有这一项**。
退出再启动 → 记录为空 → 再开一次面板又涨一次亲密。用户侧的表现是「重启刷亲密」，
更麻烦的是**产品说明和实际规则不一致**，而单测全绿——它只在同一个进程里测了两次事件。

**根因**：把两类东西塞进了同一个容器。
「同类动作 10 分钟内递减」是**软闸**，重启清零可以接受（少扣一点不坏事）；
「跨 20 小时才放行一次」是**长期规则**，它的门槛必须比进程活得久。
两者共用 `lastEventAt` 时，注释里那句「不入库：重启清零可以接受」就顺手把长期规则也一起放弃了。

**修法**：`SaveFile` 增加独立的 `dailyOpenAt?`（[src/shared/save.ts](../src/shared/save.ts)），
runtime 启动时把它镜像进 `lastEventAt`（并且只认 `Number.isFinite` 的值），
奖励真正发出时才写 `save.dailyOpenAt = t` 并落盘。
`migrate` 把垃圾值（NaN/Infinity/字符串/null）收敛成「这个键不存在」，
`toSaveFile` 在没有时**连键都不写**——`exactOptionalPropertyTypes` 下写 `undefined` 会变成 `null` 落盘。

**怎么验**：三条新单测（`test/stats-runtime.test.ts`、`test/save.test.ts`）——
① 第一次奖励 → 落盘 → 用落盘的档**新建一个 runtime** → 20 小时内再开不再给，也不为此写盘；
② 跨过窗口后重新给；③ 垃圾值经 `migrate` 后键不存在，且绕过 migrate 直接塞进 runtime 也不认。
写侧单独钉一条：`toSaveFile` 漏掉这个键的话，读侧测试照样全绿而功能永久失效。

**教训**：**门槛跨多久，状态就得存多久。** 凡是「比一次运行活得久」的规则，
它的判据不能只放在进程闭包里；而这类 bug 单测抓不到，因为测试和实现共享同一个进程生命周期——
要测就得**显式造第二个 runtime**，拿第一份落盘的档喂它。

## 4.9 经验结算追加在 applyEvent 之后：每一次都被自己的防刷闸砍半

**症状**：给「等级」写测试时，第一次喂食经验 +0.2 对，第二次（10 分钟后）+0.1 也对，
第三次隔了 11 分钟本该拿全额，结果还是 0.1。实现是我刚写的，看起来一行都没错：

```ts
const applied = applyEvent(save.stats, e, { now: t, lastEventAt })
save.stats = applied.stats
lastEventAt = applied.lastEventAt        // ← 上一次的时刻被更新成「此刻」
const gain = expGain(e, { now: t, lastEventAt, stats: save.stats })   // ← 再读它
```

**根因**：`expGain` 里那道 10 分钟递减闸读的就是 `lastEventAt[kind]`。
`applyEvent` 已经把它写成 `t`，于是 `now - last = 0`，**任何一次结算都落在窗口内**，永远减半。
这类错不会抛异常、不会让旧测试变红（亲密度的增益是在 `applyEvent` 内部算的，不受影响），
只有新写的那条时序测试能抓到。

**修法**：把经验算在 `applyEvent` **之前**，和 `eventDeltas` 共用同一个 `ctx`：

```ts
const ctx = { now: t, lastEventAt, stats: save.stats }
const deltas = eventDeltas(e, ctx)
if (Object.keys(deltas).length === 0) return
const gain = expGain(e, ctx)             // 必须在 applyEvent 改 lastEventAt 之前
const applied = applyEvent(save.stats, e, { now: t, lastEventAt })
```

**怎么验**：`test/stats-runtime.test.ts` 那条「第一次全额 → 5 分钟后减半 → 距上一次 11 分钟恢复全额」
（0.2 / 0.3 / 0.5 三个累计值）。写这条时才发现自己把窗口读成「距第一次」——
**时序测试要按上一次的时刻算，不是按第一次**，这也是它顺手教的事。

**教训**：任何「读同一份防刷/门槛状态」的新结算，必须排在**写它的那一步之前**；
往函数末尾追加代码时，先问一句它读的数有没有被上面几行改过。
