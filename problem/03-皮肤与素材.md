# 皮肤与素材

---

## 3.1 不显式写 libvpx-vp9 会**静默**丢 alpha

**症状**：编码出来的 webm 看着正常，放进桌宠却有整块底色。
**根因**：FFmpeg 默认编码器不做 VP9+alpha；`yuva420p` 之外的路径还会把 alpha 做色度二次采样，
边缘发虚。全程没有任何报错。
**修法**：编码参数定死：`-c:v libvpx-vp9 -pix_fmt yuva420p -crf 8 -b:v 0 -auto-alt-ref 0`。
**怎么验**：`npm run alpha:check`（`tools/alpha-report.mjs`）对每段动画抽帧统计背景区 alpha 分布，
超阈值就报 `haze:true`。
**教训**：素材管线必须有闸门。静默失败的编码参数，靠人眼在桌面上发现是最贵的做法。

## 3.2 体检说"有灰底"，其实是我自己把色块画到了框外

**症状**：占位皮肤 `idle/patrol2` 报 `haze:true`。
**根因**：不是抠像残留——那段动画里的色块**水平移动出了 `bodyBox`**，
体检按"身体框以外的像素应当透明"来算，就把合法内容算成残留。
**修法**：占位素材改成原地浮动，横向摆幅压在 `bodyBox` 内；同时暴露出真正的规则：
**每段动画的可见内容不许出框**，轮廓剧变的动作必须用 `animationMeta.<名>.bodyBox` 覆盖。
**怎么验**：`alpha:check` 6 段全 `haze:false`；`tools/make-test-skin.mjs` 是这些规则的活标本。
**教训**：工具报"脏"的时候先怀疑素材合不合法，别急着改工具的阈值。

## 3.3 体检只查首帧 → 漏检；查多帧 → 误报为 0

**症状**：多个帧的 `bgSamples` 一直是 0，明明该有样本。
**根因**：`analyzeFile` 里 `worst` 初始化成"全零对象"，于是"最坏帧"永远换不掉它（`0 > 0` 不成立）。
另一半问题：只看首帧会漏检——残留往往只在动画中段出现。
**修法**：`let worst = null` 起头；按 `FRAME_STRIDE` 多帧采样，报最坏那一帧。
**怎么验**：`test/alpha-report.test.ts` 直接喂构造的 RGBA 缓冲测这两条。
**教训**：统计类工具要能用"人造数据"测，不能只在真素材上跑一遍看个数字。

## 3.4 目录名叫 `xxx.webm` 也能通过校验

**症状**：审查指出 `loadSkin` 用 `existsSync` 判素材存在。
**根因**：`existsSync` 对目录也返回 true；也不检查可读、是不是合法 webm。
**修法**：改 `statSync(...).isFile()`。格式与分辨率检查留在**开发期体检工具**里，
不给生产运行时加 FFmpeg 依赖。
**怎么验**：`test/skin-store.test.ts`。
**教训**："存在性校验"不等于"合法性校验"，但边界要划清：运行时只查便宜的，贵的放工具里。

## 3.5 动画名要拼进文件路径和 URL

**症状**：皮肤契约设计期的隐患——动画名可以是任何东西。
**根因**：`..`、`/`、`\`、`?`、`#` 这些字符能把 `app://skin/...` 指到皮肤目录外，
或把 URL 查询串吃掉。
**修法**：名字必须匹配 `/^[a-z][a-z0-9_-]{0,39}$/`（池名同理，长度 31）；
`mapAppPath` 再做一次包含性检查，越界返回 400 而不是抛异常；
装载失败**逐条列错**，不静默回退默认皮肤。
**怎么验**：`test/skin.test.ts`、`test/protocol-path.test.ts`（三条穿越用例）、
`e2e/skin-check.mjs` 里"越界皮肤 id 被挡掉"。
**教训**：写穿越测试前先用 node 实测 `new URL()` 会怎么规范化——`..` 和 `%2e%2e` 的行为不一样，
凭印象写的断言三条全错（见 [06-测试探针与工具链.md](06-测试探针与工具链.md)）。

## 3.6 皮肤权重要生效，就得先承认它是**池级**的

**症状**：契约里 `weights` 到底管什么，一度写成"逐条权重"。
**根因**：想同时满足"作者可控"和"实现简单"，结果两头不清。
**修法**：契约定死：`weights` 只决定**自主活动时选哪个池**；同池内多条动画均匀随机。
缺省按池名给循环性（`idle/turn/move` 循环，`click/drag` 一次性），写了覆盖就以写的为准。
**怎么验**：`nextClip` 的单元测试 + e2e「久无人理后由皮肤权重自主选池」（走的是运行时那份 manifest）。
**教训**：契约的简单版本比完整版本更容易交付，前提是**写清楚它不管什么**。

## 3.7 素材边缘一圈毛刺，调抠像参数调不动——因为源拿错了

**症状**：用户原话「有毛刺」。导入 dsh-pet 素材后，角色轮廓外有一圈暗色噪点，放大看像锯齿。

**根因**：`E:/localwork/pet-animations/` 那批黑底 webm 是**抠像前的中间产物**，只能用 `colorkey` 处理，
而 colorkey 在这张角色上从原理就分不干净——深蓝头发、黑色裙子本身就是近黑色，
和纯黑背景的差别只有"亮度略高一点"。参数往松了调啃穿头发，往紧了调留一圈暗边。
真正的原因是我没先看打包版：`resources/app.asar` 里 `/assets/webm` 那 106 段是**已经带 alpha 的 VP9**
（`yuva420p`，背景 82.8% 像素 alpha<5），人家从来不需要抠像。

**修法**：`spike/dsh-asar-extract.mjs` 从 asar 里按字节切原片，**不重编码**，装成试穿皮肤。

**怎么验**：

1. 透明通道体检五段全 `haze:false`，框外 alpha 最大 1~7（抠像那版是 255）。
2. 贴洋红底出图（`overlay` 到 `color=c=0xFF00FF`）：轮廓干净，没有暗边也没有噪点。
3. 反面证据：`spike/fringe-try.mjs` 的 v3「腐蚀 1px」把角色**内部**也啃出洞——
   这一步能测出来，就说明问题不在参数而在源。

**教训**：素材"能不能直接用"要按**最终交付形态**查，别按手边那批文件查。
打包版（asar / 安装包）里发的才是运行时真正在用的东西，散落在目录里的往往是中间产物。
下次接手第三方素材，第一步是解开它的包看清单，而不是先调滤镜。

## 3.8 图标能放大不等于文字放得下：气泡的底图要先量内切可用区

**症状**：要拿 Kenney Emotes 的空气泡（`emote__`，32×38）当聊天气泡底图，
第一反应是「32 宽放大 4 倍，放两行字绰绰有余」。

**根因**：整图尺寸不等于可用区。按 RGBA 逐像素量下来，不透明 853 个像素里白色只有 604（70.8%），
**最大的完整白色矩形只有 20×20**（位于 (6,6)），下面 5 行是朝下的尾巴。
按 32×38 排版文字，第一行就会压在描边上。

**修法**：按量出来的 80×80（4× 之后）定正文上限——13px 字号一行 4 字、最多 4 行 = **24 字**，
超出由 `clamp()` 截断加省略号，且这条上限写进单测（台词表每组都不许超）。
尾巴占掉的那 5 行不进文字区。

**换成 Pixel Style 5 又换成 6，两次都重新量过**（同一套方法，不是拿旧数字改注释）：这两枚都是 16×16，
身子占第 0..12 行、尾巴占 13..15。但**内腔边界不一样**：
- Style 5：最大完整白色矩形 12×13 在 (2,0)，白色一直铺到第 0 行——描边只剩 8 个 `#E6E6E6` 的角像素。
  按 10 倍放大到 160×160，身子 0..130 里全是白的，文字区 120×78 加按钮塞得下。
  **代价是「没有边」**：浅色桌面上它读起来就是一堆飘着的字，边框完全看不出来。
- Style 6：第 0 行和第 12 行整条是蓝色描边（158,194,233），纯白内腔收缩成第 1..11 行 → 显示 **10..120**。
  于是原来那条「不许超过身子 130」的线不够用了：回应按钮底边 122 正好压在描边上。
  现在边界叫 `BUBBLE_INNER_BOTTOM = 120`，按钮收进 96..118。

`BUBBLE_W/H` 与 style.css 的 width/height、`BUBBLE_INNER_BOTTOM` 与文字/按钮的 top+height
都由 `test/config.test.ts` 钉在一起，改一处忘另一处会红。**这次就红了**：改了 config 的 `BUBBLE_H`
忘了 CSS 那条 `height`，测试直接指出「两个数不是同一个」——这条钉子值这个价。

**再换成 Vector Style 2 时发现：粗细不是只能挑，还能改。** Style 2 的描边是 2 个源像素，
放大 5 倍就是 10px，和 Pixel 那版一样粗；而放大到「边刚好一半」的倍数，气泡又小得装不下字。
于是 `spike/emote-thin.mjs` 直接改图：按「离外沿几层」做一次 4 邻域 BFS，只保留最外 1 层当描边，
更里的非白像素全刷成白色。副作用是**内腔跟着变大**（26×26 → 28×28），文字与按钮的 top/height 全部重算。
还有一条反向的：Vector 图**不能**留 `image-rendering: pixelated`，抗锯齿圆角会被拉成阶梯——
所以那条测试也跟着翻了个向（现在是断言「不许出现 pixelated」）。

**嫌气泡太高也不能整体缩小**：等比缩到 4 倍会连描边一起变细（用户刚要求过「一半粗」），
横向缩还会挤压文字区。正解是**只删身子中段**：`spike/emote-shorten.mjs` 删掉第 12..17 行
（32×38 → 32×32，38 高变 32 高），圆角行、描边行、尾巴行一行不碰。
脚本删之前先比对这几行是否**逐字节相同**，不同就拒绝——删错一行会在气泡身上留一道接缝，
而这种接缝在 5 倍放大下是看得见的。删完内腔变成第 1..23 行 → `BUBBLE_INNER_BOTTOM` 回到 120。

**怎么验**：`test/talk.test.ts` 逐组断言 `[...line].length <= 24`；
e2e 用 40 字的长句验截断后正好 24 + 省略号。

**教训**：拿现成图形当容器之前，先量它的**内切可用区**，不是看它多大。
带尾巴/描边/圆角的素材，整图尺寸和能放内容的尺寸经常差一倍以上。
还有一条：**描边本身也要量**——它有多宽、是什么颜色。同一个表情名在 8 个风格里，
描边能从「整圈蓝色」变成「8 个近白像素」，可用区和能不能看见边框一起跟着变。
挑不到刚好合适的粗细就改图，但改完内腔也变了，**必须重新量一遍**，不能沿用老数字。

**2026-11-05 又换了一版形状：肥皂泡 → 用户给的 `聊天气泡.svg`，量的方法也换了。**
位图那几版是逐像素读 RGBA；这一版是矢量，于是直接问 Chromium——把 SVG 内联进页面，
逐点调 `SVGGeometryElement.isPointInFill`（`spike/bubble-shape.mjs`）。
为什么不能只读 `d` 字符串：原图是**一条 path 两个子路径**靠缠绕方向凑出环 + 尾巴，
人眼扫一遍很容易把内沿当外沿。量出来：圆心 (512,512)、外沿 469.33、内腔 384、环厚 85.33，
尾巴挂在左下、下沿是一条平线（y=981.33 从 x=512 退到 x=200.53），内腔在尾巴根部还多挖出一块「嘴」。

重画时换了结构：**先铺外沿实心蓝，再盖内腔实心白**，不赌渲染器怎么解释 winding rule。
这里踩了一条只有看图才会发现的坑：第一版把内腔画成「白圆 + 白嘴」两块叠在一起，
交界处两条反走样的边重合，深色桌面上显出一道浅灰弧——数字全对（`isPointInFill` 量得出 384），
是 `spike/bubble-ab.mjs` 并排渲染才看见的。合成**一整条闭合路径**（嘴的三条边 + 一段 `A384 384` 大弧）之后接缝没了。
**教训**：矢量里「同色两块叠」不等于一块——反走样会让重叠边现形，量数字测不出来，得看图。

形状一换，可用区整个搬家：主泡从「偏下偏左的椭圆」变成「用满框的正圆」，
内腔圆心从 (101,138) 回到框正中 (110,110)、半径 82.5。于是文字与回应按钮那 110×84 一块
按**角点落在圆内**重解（最远角点 69.2 < 82.5），`BUBBLE_INNER_BOTTOM` 从 180 变 **152**。
这条不再靠注释自觉：`test/config.test.ts` 从 `bubble.svg` 里读 viewBox 与内腔弧半径，
把两块内容的四个角逐个算距离——素材改了而数字没跟上，红的是几何，不是「注释过期」。

**同日第三版：用户换成 `chat-speech-bubble-svgrepo-com.svg`，并要求「边框细一点」。**
这一版把上面两条教训都吃到了：

- 形状不一样：主泡圆心 **(256, 213.33)**，**不在 viewBox 正中**——正下方那截尾巴要占掉
  213.33..512 那一竖条，尾巴尖正好切在框底。所以「圆心 = 框的一半」这种省事假设直接作废，
  `spike/bubble-shape.mjs` 改成同时报**着墨段**与**空腔段**（空腔判据是「不是环色」而不是
  「没着墨」：参考图的腔是透明的，我们的腔是实心白，两种都得算），量出来空腔最宽行 y=208、
  段 [64,448] → 圆心 x=256、内腔半径 192 ✓ 和路径读出的数一致。
- 「细一点」落成一个旋钮：这版不再两层填充叠，而是**一条中线轮廓**（半径取内外沿的中点 202.67）
  `fill` 白 + `stroke` 蓝，环厚 = `stroke-width` = 21.33 → 220px 上 **9.2 CSS px**
  （上一版 18.3px，正好细一半）。上一条那条「同色两块叠会显出接缝」的坑于是从根上没了——
  内腔与环是同一条闭合路径的两面。
- 授权：SVG Repo 的许可页两次 429，**没核到原文**，所以不赌——依旧只借形状与比例、不搬字节。
  这条要写在这儿，是因为「抓不到」和「查过没问题」是两件不同的事（见 memory 的分证据等级）。
- 数字重解：内腔圆心 (110, 91.67)、半径 82.5 → 内容块 110×84 的角点最远 69.4，
  `BUBBLE_INNER_BOTTOM` 152 → **134**。测试不抄这些数：它从素材里读 `viewBox`、中线弧半径、
  `stroke-width` 与路径起点，自己算圆心和内腔半径，另外钉一条「环厚 ≤ 12px」防着手滑画粗回去。

## 3.9 素材的名字不是语义：`depth_` 是「只有下边多一道影」，`flat_` 是「整块实心色」

**症状**：给食物列表换底板时按名字挑了 `button_rectangle_depth_line`，以为 depth 是「有立体感」；
又有人建议格子换 `button_square_depth_flat`，以为 flat 是「平面无边框」。

**实测**：
- `button_rectangle_depth_line.png`（192×64）从外到内是 2px 灰框 + 2px 白高光 + 2px 留白 + 2px 蓝内框，
  **只有下边**再多 4px 深灰底影（116,116,135）。也就是说四条边的装饰厚度不一样：上左右 8px、下 12px。
  于是 `border-image` 的 slice 和 `border-width` 都必须写成不对称（`8 8 12`），
  写单个 8 会把下边那条蓝色内框留在被拉伸的中间区里，变成一条随面板高度漂的杂色带。
  另一个坑：CSS 把四值 `8 8 12 8` 归一化成 `8 8 12`（第四个默认等于第二个），
  计算样式读出来和源码写法不一样，断言要按归一化后的写。
- `button_square_depth_flat.png` / `button_square_flat.png` 中间是 **实心蓝**（28,159,215），
  不是「去掉边框」。真按它换格子，格子会变成蓝块配深字。
  最后格子退回 CSS 白卡（和状态栏/设置的卡片同一套语言），蓝线全场只剩底板一道。

**图标同理：`viewBox` 也不等于视觉尺寸。** 五枚图标的自然尺寸是 201×200 / 200×200 / 200×200 / 200×200 / **32×38**，
但真正决定「看着多大」的是墨迹范围：`spike/icon-metrics.mjs` 把每张画到 512×512 canvas 上读 alpha，
量出墨迹占方框 0.75~1.00、最远墨迹点 1.122~1.414 个半边长。圆底青圈内半径只有 15.6px，
所以统一 26px 方框时碗的筷子和齿轮的齿会戳出去 2.5px，而爱心和手柄空一大圈。
按实测反推逐枚定尺寸（20/24/24/20/18×21）才一致。顺带量出 `dots3.png` 是 32×38 被塞进 26×26，
横向被拉宽 18%——它还是 Kenney **Vector** 导出（28 个颜色里有半透明过渡），
所以不能加 `image-rendering: pixelated`，加了会阶梯化。

**教训**：素材名只能当索引用。边框厚度、内腔可用区、是不是实心、有没有透明边距，
全部要开文件量像素（`spike/emote-geometry.mjs` / `icon-metrics.mjs` / `plate-crop.mjs` 的自检段），
量完把数字写进 CSS 注释和测试断言里，否则下一次换素材又是按名字猜。

## 3.10 重染素材时，我把两个约束写反了：锚点用单通道、环要赢过所有邻色

「按钮背景太暗」不是猜的事，得先把颜色数学写实。CC0 素材可以改 `fill`，但改之前要回答两问：
**暗在哪一层**、**改成什么色还能被看见**。`spike/color-math.mjs` 把 OKLCH↔hex、WCAG 对比都做成可跑的函数，
量完是：面 `#DADCE7` 的 L=89.6、还带紫（H≈290），整包素材的中性灰都偏这个方向；
在浅桌面上它和桌面糊成一片，看起来不是「浅」而是「脏」。所以 A 套把面提到 L=96.4（`#EBF5FB`），
环反而要**更深**一点（`#6990A7`）才能同时对面、对浅桌面拿到 3:1——这一条我一开始推错了两次。

**错一：解环的约束模型。** 第一版 `solveRing` 取「邻色里**最亮**的」（面 / 白高光 / 浅桌面三个 `relLum` 拿 `max`），
还把深色桌面也列进要赢的对象。两个都偏：
- 对比是亮的一侧除暗的一侧，拿最亮的邻居去要求环，等于把环往近黑解——圆底变成「黑圈 + 白饼」，比原来更突兀。
  真正该管的是**最暗**的那个邻色（`min`），因为环在暗侧，瓶颈是别和面贴得太近。
- 「深桌面」这条约束本身不成立。圆底的边缘是**白高光 + 灰环两层配合**：浅壁纸靠环压住，
  深壁纸靠白高光压住（白对 `#22262C` 实测 15.7:1）。要求环单独赢过深桌面，是把两层分工当成一层。

**错二：PNG 渐变重染的锚点用了一个通道。** `button_rectangle_depth_line.png` 是灰阶渐变 + 一条青线，
想按明度分段映射到新的色阶，锚点我直接取了 R 通道（116 / 150 / 218）。但这几档灰是**偏紫**的：
`#747487` 的三通道均值是 122.3、`#9696A3` 是 154.3、`#DADCE7` 是 223。
用 R 当锚点，每个像素都会算出「介于两档之间」的插值系数，于是**没有一个像素是纯色**——
环出来是 `115,152,172` 而不是 `#6990A7`，整张图糊成一层薄蓝雾。
改成三通道均值做锚点 + 两端钳住，青线（`max-min>60`）和透明像素跳过，才得到干净的色阶。

**怎么才算落地**：色值写进 `:root`（板心三档）和 SVG `fill`（圆底四档），PNG 是二进制的所以只能靠测试。
`test/palette.test.ts` 直接解码像素钉住四件事：尺寸还是 192×64（几何没被顺手改掉）、
左边界仍是「环→白高光→留白→青内框」四层顺序、旧灰紫 `#747487` 一个像素都不剩、
青内框还是 896 个像素（重染不能把蓝线也吃掉）。
这一套必须有，因为**重装素材会把原色盖回来，而任何功能测试都不会变红**。

## 3.11 「放大后边缘很模糊」：位图放大 5 倍糊的是采样，不是分辨率不够

**症状**：用户看着气泡说边缘模糊，问能不能用 SVG 画一个类似的。

**先量，别先画**。把现图截一帧按气泡矩形裁出来放大看（`spike/bubble-shot.mjs`），
看到的不是「一条 5px 的蓝线」，而是**一条内侧一路淡到白的软带**。再沿左边缘取一列逐像素读数
（`spike/bubble-edge-ab.mjs`，同一页里把旧位图和新 SVG 并排放）：

```
SVG ：描边实色 10 个设备像素，半透明过渡 0 个
PNG ：描边实色 15 个设备像素，内半侧 158→163→172→182→192→202→211→221→231→241 一路淡上去
```

也就是说 1 个源像素的描边放大 5 倍后，**内半侧摊开约 4.5 个 CSS 像素**（2× 屏上 9 个设备像素）。
这是双线性重采样的正常结果，不是「图太小」——同一张图无论放大到多少倍都会摊这么宽。
顺带一个容易读错的点：气泡外沿那一列的 **alpha 是硬跳 0→255 的**，
所以「有没有模糊」不能只看 alpha，得看 RGB 从描边色到纯白跨了几个像素。

**修法**：按原图逐行量出来的轮廓重画矢量（身子外沿 0..32×0..26、四角外半径 2、尾巴 45°、底开口 14、尖台 4），
描边路径走**中心线**（内缩 0.5）配 1 单位宽描边，这样最外一圈还是 1 个源像素——
内外边界和位图版一个像素都没差，`BUBBLE_INNER_BOTTOM` 那套文字/尾巴的几何契约原样不用动。
两个细节：① 尾巴和身子必须是**同一条闭合路径**，分成两个图形画会在接缝处多出一道横线；
② 原图尾巴尖端是被 32 行裁出来的 4px 平台，不是尖角，照画才像。

**教训**：位图素材的显示尺寸一旦明显大于源尺寸，边缘质量就由采样方式决定，靠「换更清晰的图」解决不了；
要么给矢量，要么给按目标尺寸重出的位图。判据也简单：**数描边色到纯白跨了几个像素**，跨得宽就是糊。

## 3.12 为了一块底板学的九宫格，最后整块框被否掉：先问值不值，再学怎么写

**症状**：食物列表的底板一路改成这样——四层边的 `button_rectangle_depth_line`、不对称 slice `8 8 12`、
`background-clip: padding-box` 配对、PNG 按明度分段重染（§3.9、§3.10）。
用户看完 A 套配色之后说的是：「点击喂食时，食物列表我不想用外边框了，能不能像状态那种，做一个简单的。」

**根因不在实现，在前提**。三块副板（食物列表 / 状态读数 / 设置行）是同一级的东西，
其中只有列表带一圈素材框，读起来就不是「列表更重要」，而是「这三块不是一套」。
装饰的成本我们全部付过：不对称 slice、中心色要靠 CSS 递进去、圆角外侧透明缺口要专门防、
重染要处理渐变锚点——这些复杂度**全部来自「要这一圈框」这一个决定**，而这个决定当时没人问过值不值。

**修法**：`.pet-plate.is-foods` 整条规则删掉，列表回到基类那张 CSS 卡片
（`--plate-fill` 板面 + 1px 描边 + 10px 圆角 + 6px 留白），和另外两块完全同一处理。
素材 `button_rectangle_depth_line.png` 是**删文件**而不是「留着没人引用」——
`tools/copy-static.mjs` 按目录搬，留在仓库里就会跟着进 dist 发出去。
退场要一次退干净：CSS 规则、素材文件、`test/palette.test.ts` 里那四条解码像素的断言、
e2e 里钉 slice/厚度的那几条、README 那段「外板用 Kenney 素材」的规则句。

**怎么验**：`test/palette.test.ts` 现在钉的是反方向——CSS 里不许再出现 `border-image`，
且那个素材文件必须不存在；e2e 改钉卡片形状（1px 描边、10px 圆角、6px 留白、投影带负 spread）。

**教训**：给 UI 加一层素材装饰之前，先问一句「同级的那几块也有吗」，
再问「这一圈框要付出多少实现成本」（不对称切片、色彩重染、圆角缺口都是它的隐性账单）。
§3.9 那些量出来的数字仍然有效——它们是**任何 border-image 素材**的通用知识，只是这个产品现在不用了。

**顺带一个自伤**：新加的「CSS 里不许有 border-image」那条测试一开始把自己判红了，
因为 style.css 的注释里写着「以前这里是一整块 border-image 九宫格」。
**读 CSS 形状的断言必须先剥注释**（同一类事在 `image-rendering: pixelated` 那条上已经发生过一次），
否则注释里提一句属性名就等于改了一次实现。

## 3.13 名字在装载时被丢掉：点火锅播到白饭的吃相

**症状**：不是用户报的，是我在写「吃饭时别打断动画」那条 e2e 时撞出来的。
README 一直写着「点某一格播它对应的那条吃动画」，我去核对代码时发现这句话不成立。

**根因是两份真相**。食物表里每格都存了 `anim: { pool: 'eat', name: 'rice' }`，
`name` 一路传到渲染层，然后**被丢掉**：

```ts
if (!requestClip(f.anim?.pool ?? 'click')) requestClip('click')   // 只递了池名
```

而 `requestClip(pool)` 里面是 `picker.pickFrom(source, pool, current)` —— 池里随机挑一条。
所以点哪一格都是「eat 池里随便一口」，六格里只有六分之一概率对上。

再往下挖一层，丢掉名字是**装载时就发生的**：`loadSkin` 把 manifest 摊成
`pools: Record<池名, 条名[]>`，池内只剩一串名字、没有语义；
`REQUIRED_POOLS` 又是「每个池都必须非空」——于是任何自带皮肤只要声明了 `eat` 池，
就必须给它一条 clip，可食物表里有六口，**只给一条就五口播错，给六口就逼默认皮肤做六段动画**。
结构上就没有「皮肤可以做其中几口」的位置。

**修法**：把名字接回运行时，而不是把语义塞回装载。
① 随机层加 `pickNamed(skin, pool, name)`：查的是皮肤**实际有什么**，有就给整条引用，没有返回 null；
② 渲染层按名字点歌，皮肤没做这一口就**回落到 click**——
   绝不「随机给一口别的」，因为播错的那口会假装它吃的是别的东西，比不播更误导；
③ 占位皮肤 `skins/block` 的 eat 池故意只做 `rice` / `hotpot` 两口：
   e2e 于是同时覆盖「按名字命中」和「没做这一口 → click」两条路。

**怎么验**：`test/behavior.test.ts` 的 pickNamed 三条（命中给整条引用、没这个名字给 null、
空池给 null）；e2e 两条（点白饭该是 `{pool:'eat',name:'rice'}`，点饺子该是 click）。
注意断言要拿**整条引用**比而不是只比池名——只比池名的话，随机播到同池另一条也算过，
那正是这个 bug 的原样。

**教训**：契约里存了字段，运行时却没人读它，比压根没这个字段更危险——
文档、类型、数据表都写着「按名字」，只有代码不是。加一条 e2e 断言到**整条引用**就能长期钉住。

**同日第四版：换成圆角矩形，环再细一半（用户：「边框还是太宽」「圆形气泡能不能换成矩形的」）。**
形状从「圆 + 尖」变成「圆角矩形 + 底部居中的三角尾巴」，两条老账重新结了一遍：

- **框不再是正方形**：viewBox 440×320 → 显示 220×160。`BUBBLE_H` 一改，
  `test/geometry.test.ts` 里 bubbleAnchor 那四条硬期望全要重算（每条都是「锚点顶 − 12 − 气泡高」），
  这就是它们当初被写成字面量的代价——好处是算式一眼可核，坏处是改尺寸必须人跟着动。
- **环厚回到「一个旋钮」**：`stroke-width` 12 单位 → 6 CSS px（历史 18.3 → 9.2 → 6）。
  下限也钉了：低于 4px 在 2× 远程桌面上会开始发虚，所以测试两头都卡。
- **必须是一条闭合轮廓**。中途试过「`<rect>` 画身子 + 一条开路径画尾巴」：尾巴本身没问题
  （开路径的 fill 会隐式封口、stroke 只画两条斜边），但矩形那条**底边的描边**会横穿尾巴根部，
  看上去像尾巴被一道线封口。一条路径把「底边 → 下尾巴 → 回底边 → 圆角」走完整条就没有这道线。
- **内腔判据从圆回到矩形**：`BUBBLE_CAVITY = {x,y,w,h,r}`，内容块四角先验矩形界、
  再看有没有哪个角落进「两个方向都进了角区」那块（那里才要躲圆弧）。
  文字区从 110 放宽到 150，24 字排得更松——圆腔时代那个「下半截本来就窄」的约束没了。
- 素材与 config 之间能机器核对的只剩两条关系：**显示比例 = 素材比例**、**环厚 = `BUBBLE_RING_W`**。
  上一版靠解析路径里的弧半径与起点反推圆心，这版路径是矩形 + 尾巴，那种解析不再划算，
  所以圆心/半径这类派生量收进 config（算法写在那条注释里），测试负责核对上面那两条关系。

**教训（补一条）**：形状每换一次，「内容块怎么解」就换一次模型——圆要解角点到圆心的距离，
矩形要解四角对矩形界和圆角区。真正稳的做法是把**内腔本身**当成一份有名字的数（`BUBBLE_CAVITY`），
换形状时换的是这份数的算法，而不是让每个调用方各自回忆上次怎么算的。
